# reconcile（事项追踪）

一个常驻在 Paseo daemon 里的**对账控制器**：定期读外部系统（项目跟踪系统、版本库的提交记录、按 URL
拉的开关文件），按私有规则判断每件事卡在哪、下一步该谁动。**能读到的先自己读**，读不到或者几处说法对不上，
才在 Paseo 里起一张**问题卡**问你，你的回答就是下一步的依据。判断全是确定性代码，不调模型、不花 token。

典型用法：单子关了不等于外放了，外放了不等于灰度全量了，这两步单子上没人记。规则从单子正文和关联提交的
diff 里找灰度 key，看提交什么时候进了各地区的发布分支、外网版本文件是不是在那之后出的包、外网开关文件里这个
key 是多少，自己判断外放、灰度中、全量、回退。外放在后台核对：外放日过了还没进发布分支、或者进了但外网版本一直
没动，就在这个事项上写一句提醒（陈述，不是问题），同时发一张只有「知道了」（外加「其他」，顺手说的一句记在单子上）的
卡；确认过的同一个情况不再提醒，情况变了才再发。靠整目录复制同步的发布分支，那次复制就是封版：一读到新的复制，
目标是紧接着那一班的单子里有提交没被带进去，马上用同样的卡说一声（比外放日之后的提醒早），单子进入「等单独
merge」阶段，它的提交出现在发布分支上就往下走。只有 key 找不到或有好几个、key 从外网文件里消失这类说不清、又影响
下一步的情况才问人。

## 模型

- **来源（source）**：只读地拉外部系统，变化记成观察（observation）。拉不到时退避重试，连续失败标成不可用。
  一个判断依赖的数据最近没读到，它就带上「数据可能过时」，规则据此要问的问题先不发，等读到了再说。「依赖」按读过什么算：
  单子自己的来源、开关文件（每个判断都从它们认 key），以及规则通过 `ctx.item` / `ctx.observations` 查过的每一项；
  规则也可以在承诺上写 `uses` 说明这个问题只依赖哪些：数据项的 key，或来源 id（它的任何一份文件过时都算）；
  `uses: []` 就是只依赖单子自己的来源。写了配置里没有的名字，这次判断按规则出错算，不会悄悄什么都不压。示例规则的封版提醒
  只看版本库，所以版本文件读不到不会压住它。一个来源（或开关来源里的一份文件）连续 `sourceDownHours` 小时读不到，
  给 admin 发一张只有「知道了」的卡，写明哪个来源、从什么时候起、最后一次的错误；同一次故障只说一次，读到了卡就撤掉，
  一周没人回就过期（不算评测候选）。没有 admin 时页面上写明没人收故障卡。被压住的问题兜底时间照走，所以
  `sourceDownHours` 要比规则里最短的兜底间隔短，否则问题可能一次没问就过期了，故障卡还没到。
  两种：
  - `gcp`：项目跟踪系统，经它的命令行工具调网关（`gateway` 里配路径和目标）。列表按页拉回（按返回的 `total_page`，
    一页满了也接着读，一轮最多 10 页；返回的 `total_count` 和读到的条数对不上会在来源的错误里说，读到的比它说的少时
    回溯窗口不前移，下次常规轮询再列一遍）状态、更新时间和配置的几列（`columns`）；只有值得的行才详读（单子正文、关联提交、
    操作历史），详读时按 `changes` 用只读的 `svn log` / `svn diff` 看每个提交是在哪个分支提交的、新加了哪些标识符、
    现在哪些分支里有它、什么时候进去的，以及靠复制同步的分支最近一次从它所在分支复制是哪次（`copied`，封版）。热的单子可以按 `refreshHotMinutes` 定期重读，看提交后来进了哪些分支。
  - `flags`：按 URL 拉几份 JSON 开关文件，把配置的几节摊平成「节.key → 值」，一份文件是一件 item。每次的代价
    和单子多少无关；值变了才算观察，只叫醒关联到这个 key 的事。`sections` 里写 `""` 取顶层的标量，`itemKind`
    换成别的（比如 `version`）就只是一份被读的文件、不当开关来源，外网版本文件就这样接。
- **关联**：一件单子关联到哪些开关 key，是确定性的交集：开关文件里所有的 key ∩（单子正文 + 关联提交 diff 里净
  新增的标识符）。每个命中带证据（单子哪段文字、哪个提交的哪一行），规则拿 `kase.flags` 用。开关条目里像标识符的
  字符串值（比如版本检查函数名）算这个 key 的别名，只在单子自己的提交新加了它时才算，和直接命中分开记（`aliases`）。
  规则还能看兄弟单（`ctx.siblings`、`ctx.flagsOf`）：示例规则按「直接命中 → 唯一的别名 → 兄弟单的 key 作候选再问」认 key。
  灰度是 key 层面的事：自己的提交新加了这个 key 的单子是主单（好几张时取外放日最晚的），别的对上同一个 key 的单子
  外放后跟着主单走、不单独问，主单结束时一起结束；主单这一轮没在跟（冷了或者没跟踪）时才自己问（`ctx.naming`）。
  别名只认规则列出的字段（示例规则的 `aliasProperties`），分支名这类字段的值说明不了是哪张单。
  别名来自「能力检查」类字段（示例规则的 `capabilityProperties`）时不算 key，而是一条依赖边：这张单提供 key 需要的能力，
  外放了就结束，并叫醒持有这个 key 的单子（规则输出 `wake`，被叫醒的单子在最近 `recentDays` 天里算热）。
- **冷热**：每轮只判断热的事。热 = 有没结束的承诺，或在关注列表里，或最近 `recentDays` 天有人（不算 API 用户和
  自动化规则）改过，或 `dateFields` 里的日期在前后 `dateWindowDays` 天内，或关联的开关最近变过。冷的不判断、
  不显示、不详读，列表里它的状态或配置的列变了才重新看。标题里有 `coldTitles` 之一的（总单、长期维护单这类）
  只有有没结束的承诺或在关注列表里才热，但照样当父单：子单照常跟，兄弟单推 key、依赖边不受影响。
  单子正文和提交里都只认「像个名字」的 key（带下划线、数字或驼峰）；`test`、`Ratio` 这类普通词的 key 两边都认不出来，
  这样的单子只能靠问人要 key。
- **规则（rule）**：私有的 `.mjs`，输入是单子当前的样子、最近的观察、已经记下的事实和这件事的承诺，输出是
  阶段、一句话现状、下一步谁动，以及**承诺（commitment）**：「某个时间问某个人某个问题」。规则是**受信任的代码**：
  它来自私有配置目录，能改这个目录的人本来就能改插件的行为。约定是规则不读时钟、不 import、不联网，所有东西都从
  `ctx` 和 `kase` 拿；加载时用正则扫一遍源码挡住明显的写法（`Date.now()`、无参的 `new Date()`、`import`、`require`、
  `process` 之类），运行时入参是冻结的，输出按 schema 校验。**这不是沙箱**：绕开扫描的写法有的是，规则跑在插件进程里，
  也没有超时，死循环会卡住整个控制器。把 `Date` 换成固定值、给规则调用加时间上限，是以后的事。
- **承诺**按 key 去重，规则每次重算都只是「确保它在」。到点了按人的不打扰时段和每天的上限决定发不发；同一个人
  同时到期的几个问题并成一张卡；没人答按 `nag` 再问，问满了等兜底时间到期。下一步问什么由规则根据上一个
  回答推出来，控制器不知道「外放」「灰度」是什么。承诺的 id 由 key 算出来：同一个 key 一旦答过、过期或取消，就
  再也不会重建，所以规则要在 key 里放上能区分「这一轮」的东西（示例规则用日期、轮次、出了什么情况）。规则把触发时间
  改晚了，已经问过的这一轮会收回，到新的时间再问。
- **问题卡**：插件自带一个没有模型的 provider（`reconcile/inbox`），一张卡就是一个这个 provider 的 agent，放在
  名为「事项追踪」的 workspace 里（2026-10-23 之前叫「事务」：同一个 workspace 按记下的 id 和目录找回来，插件一启动就改名，不换新的；人自己改过的名字不动）。它在对话里先写清楚已知的情况，再发一个 `question` 权限请求——App 把它画成原生的
  选择题（选项 + 「其他」），并推到手机上。选项、在「其他」里写字、直接在对话里打字都算回答；收起不算，到下次
  追问时间会再问。答完的卡会被归档。人在侧边栏里归档一张没答的卡，90 秒后算「关掉了」；Paseo 退出时会先关掉所有 agent，
  这种关掉不算，重启后同一张卡会再起一个载体（不打扰时段里先不起，到能打扰时再起，也不重复占每天的额度）。
- **同时投递**：人的配置里有 `notify`（渠道 id 和地址，渠道由别的插件注册，比如某个 IM 插件），卡起来的同一刻经宿主的
  `server.deliver` 给每个渠道发一条：标题是卡的标题；只有「知道了」的陈述发全文，问题发问题和选项，最后一行写
  「在 Paseo「事项追踪」里回答」（渠道里不能回答）。每张卡只发一次：重启后给同一张卡再起载体不再发，并成新卡才发新的；
  发给渠道的 `idempotencyKey` 也按卡取。卡不起就不发，所以不打扰时段和每天的上限照样管着。发失败不挡卡，页面上写明
  原因，之后每轮对账再试，一共最多 3 次。宿主没有 `server.deliver` 时卡照常起，页面上写明渠道收不到。演练时计划里
  列出「会发 <渠道>：<标题>」，不真发。
- **日志**：所有判断和动作按事件追加进 `<dataDir>/journal/YYYY-MM.jsonl`，定期写快照；重启时重放。每次对账写
  `status.json` 和 `plan.md`（这一轮打算做什么、在管的事）。

## 配置

插件设置（设置 → 插件 → 事项追踪）：

| 字段 | 意思 |
|---|---|
| `configDir` | 私有配置目录，见下 |
| `home` | 这个控制器该在哪个 `PASEO_HOME` 下发卡。和 daemon 的不一致时只演练 |
| `mode` | `dry-run`（默认）或 `live` |
| `instanceId` | 这套部署叫什么，记进日志 |
| `tickSeconds` | 多久检查一次，默认 60 |
| `dataDir` | 日志放哪，默认 `<PASEO_HOME>/plugin-data/reconcile` |

私有配置目录（不进这个仓库）：

```
persons.json       { "<id>": { name, admin, tz, quiet: { work?, personal?, family? }, pushPerDay,
                                notify?: [ { channel, to, label? } ] } }
sources.json       [ { id, label?, kind: "gcp", command, gateway: { path, tool, target }, gcpHost, projectId,
                       lookbackDays, watch, activeHours,
                       everyMinutes, offHoursEveryMinutes, maxCallsPerHour, timeoutSeconds, domain,
                       columns?: { <列 id>: <字段名> }, watchEveryMinutes?,
                       journals?: { automationNotePrefixes },
                       refreshHotMinutes?,
                       changes?: { command, timeoutSeconds, maxRevisions, recheckMinutes?, maxCallsPerPoll?,
                                   repos: [ { name, pattern, branches: [ { name, url, copied? } ] } ] } },
                     { id, label?, kind: "flags", files: [ { id, url, labels } ], sections, itemKind?, activeHours,
                       everyMinutes, offHoursEveryMinutes, maxCallsPerHour, timeoutSeconds, domain } ]
policy.json        { tz, ruleBreakerChanges, sourceDownHours,
                     hot?: { recentDays, dateWindowDays, dateFields }, coldTitles? }
calendar/<年>.json { holidays: [日期], workdays: [调休上班的日期] }
rules/*.mjs        规则；examples/release-followup.mjs 是一份可以照抄的
```

`quiet` 里写的是**可以打扰**的时段，比如 `"workdays 09:30-20:00"`、`"daily 08:00-23:00"`；`workdays` 按日历算节假日
和调休。`command` 是不经 shell 直接起的跟踪系统命令行工具，写绝对路径：`["<node.exe>", "<…>/cli.js"]`，
要先在这台机器上登录；`gateway` 是它调用网关用的路径、工具名和目标，只写在私有配置里。缺某一年的日历时状态里会提示，
按周一到周五算。

`changes.repos[].pattern` 是匹配跟踪系统里提交编号的正则，第一个捕获组是版本号；`branches` 按顺序试，第一个
`svn log -c` 有这个版本的就是它提交的分支。靠**整目录复制**（不是 merge）从别的分支同步的分支，把复制的目录写进
`copied`：对这些目录问 `svn log -c`（会顺着复制历史找到），找到了就用这次复制（`--stop-on-copy` 的第一条）的
revision 和时间当「进分支的时刻」；还没进的过 `recheckMinutes` 再问。`journals.automationNotePrefixes`
是自动化规则写的备注前缀，这类改动不算「有人改过」。`files[].labels` 原样给规则，用来区分环境和地区。
一张单子关联的提交里有一个读不到（网络、服务器），这张单这一轮不算读过，下一次正常轮询再读，不会带着缺了的提交去判断；
svn 说「那个分支在那个版本还不存在」不算读不到。连续 3 次都读不全（比如某个分支这个账号没有权限），就按读到的收下，
标成不完整（`incomplete`），页面上提示；示例规则对不完整的单子不说封版和外放的提醒。

## 列表和事项页（流程图）

**列表**按「现在该谁动」分组，不按健康度：要你做的、检查出错的、在等别人的、系统在查的、你自己在开发的、结束了的。
「要你做的」总是显示，空的时候说没有。每行：一句现状、沿着常规路线走到哪的一条细格（走过的、现在的、还没到的；走过岔路的在格子旁标出来）、
球在谁手里和等了多久、接下来会发生什么。规则对这件事的陈述（`notice`，「看着不对」）和「数据可能过时」不管事项处在什么状态都写在行里。
点一行进它的页面；别的屏带 `case` 参数也能直接打开某一件。
来源在页面上叫它的 `label`（`sources.json` 里每个来源可以写一个）；没写的只说「N 个来源」，id 只在证据页里。

**事项页**从上到下：一句话的状态条（颜色就是球在谁手里：你 = 黄，系统 = 蓝，别人 = 灰，坏了 = 红，结束 = 绿）；四格（走到哪、在等谁、
等了多久、要你做吗）；有问题等你就在这里答；阶段图（点一段看那一段的细节）、经过、证据三页；旁边是接下来会做什么、关联的事项、你在对话里说过的话。
窄屏（手机）是竖排。

**规则怎么声明阶段**：`stages` 里每一项可以是一个字符串（和以前一样，就是一个阶段的 id），也可以是对象：

```js
stages: [
  "open",                                              // 字符串：没有名字，页面上叫「第 1 步」（不显示 id），走常规路线的下一步
  { id: "review", label: "评审", done: "评审通过" },     // label: 页面上的名字；done: 「已经走过这一步」的标志，一句话
  { id: "rework", label: "返工", side: true, when: "评审打回时" },   // 岔路：不在常规路线上，回到声明在它后面的第一个路线阶段
  { id: "finished", label: "完成", end: true },        // 结束；endKind 是 done（缺省）/ dropped / other，只有 done 算常规路线的终点
]
```

`next`（数组）写出这一步通常去哪，缺省是常规路线上的下一个。不合规矩（重复的 id、指向不存在的阶段、`endKind` 没有 `end`、
`when` 没有 `side`、岔路又是结束）的规则按那个文件加载失败算，原因写在页面上。规则的输出还可以带一个 `since`：它从跟踪系统的证据
知道这一步是什么时候到的（一个时刻，带不带时区都行，不带的按实例的时区读；晚于判断时间的不认，早于上一步到达时间的也不认）；没有就只有「检查到它的时候」。
没写 `label` 的阶段在页面上叫「第 N 步」、岔路叫「岔路 N」、结束叫「结束 / 不再追踪」，id 只在证据页里（那是写规则的人的词）。**这些只影响页面怎么画，不改任何判断。**

**阶段历史从日志折叠出来**，不用改日志：状态里每件事只留最后一次判断，但日志里每次判断都有，一次停留就是同一阶段的连续判断。
所以老日志（没有 `since`、没有阶段名字）也能画；页面上会诚实地标出什么是推的：
- 开始追踪之前的阶段（路线上排在第一次看到它的阶段前面的），没有记录，只画「开始追踪时已经过了这一步」，不给时间；第一段的开始时间是第一次看到它的时间，页面标「追踪前」。
  从这个时间起算的时长列表和四格也写「至少」（「至少已等 1 天」「至少用了 3 小时」）；第一次看到时就已经结束的，不编一个时长，写「追踪前就结束了」。
- 每一段有两个时间：**到达**（规则从证据说的 `since`，有就用它）和**发现**（对账第一次看到它在这一阶段）；差得多时页面两个都写。
- 为什么换阶段（`cause`）是读出来的：中间有人说了不再追踪 → 你说的；说了判断错了 → 更正；规则文件也换了、而这件事的数据（或每件事都读的开关文件）没变 → 规则改了，那一段
  之前的判断不算它走过的一步，不画；其余算数据或时间。「规则改了」是对巧合的解读，不是证明：数据变化和规则改动落在同一轮时会读成数据。
- 跳过、打回、规则没声明的阶段：页面标成「跳过」「打回」「岔路」，原因写在旁边。规则以后不再声明的阶段，老判断里还有它，就当成一个没声明的岔路画出来，不丢。

**在页面上回答问题**：确认某句话是不是本人说的那类问题（确认卡）只显示、不在页面上答，页面给「去确认卡上答」。起卡的那几秒里页面上答了，答案算数：卡不再起（已经起来的收掉），起卡失败也不会把问题放回去再问一次。
`reconcile.answer` 和问题卡的表单走同一条路径（同样的记录、同样的后续），页面和卡片谁先到谁算，后到的被告知
「已经答过了」，什么也不记；卡片上没有别的问题了就当场收起，还有别的就在下一轮检查时缩成剩下的。**批准对外的动作不在这里做**，只在审批卡上点。
页面答的是问这个问题时指定的那个人的问题，插件只有一个管理员在用，没有再核对是谁在点。

**流程（flow）**：页面上有「流程」一段，读编排运行时写的事件文件（`<logDir>/runs/*.jsonl` 和 `.claim`，路径的找法和运行时一样），**只读**。
一次运行属于哪件事，只看启动它时给的 `--affair`：`link` 指向本插件的屏（`plugin: "reconcile"`、`screen: "inbox"`），`params.case` 是事项的 key，`params.stage` 可选。
没有别的关联办法。**活着不是这里判的**：是运行时的那张表（`orchestration/runtime/liveness.mjs` 的 `classify`），`shared/liveness.mjs` 是它的一份拷贝
（`orchestration/` 里 `npm run sync:liveness` 复制，头部标着「由运行时复制，别手改」），测试比对文字相同、并逐行按 `orchestration/fixtures/run-state-cases.json` 测。
读的事实和运行时一样：占位文件的修改时间（2 分钟内）和内容、持有者那台机器上 pid 是不是已经不在（不在就是死了，不管占位多新）；没有占位的旧文件用 `run.start` 里的 pid，再看最后一条事件是不是 15 分钟内。
「可能卡住了」用 orchestration-ui 同一个公式（`staleAfterMs`）：活着、但安静得比 max(15 分钟, 正在跑的调用开始 + 它的超时 + 2 分钟 − 最后一条事件) 还久；等人闸的不算卡住，算「在等你批准」。
**哪次运行说了算**：每个阶段只看最新的一次（失败了又跑成功的，失败是历史）；事项已经离开的阶段里坏掉的运行（失败、断了、安静太久）不再算；没写阶段的运行算当前阶段的。
旧的运行仍然列在「流程」一段和「经过」里（起了流程、怎么结束的）。失败、断了的流程的状态条只说「看一眼」，现在页面上没有「重试」「我自己来」。
**事件文件里的字不可信**（能写 logDir 的人都能写）：显示前一律截短、去掉控制字符和看不见的字符（清单是 `orchestration/fixtures/affair-cases.json`），「去批准」只打开长得像 agent id 的那个 agent；
读文件也有上限：一个文件是不是本插件的，只读开头（第一行超过 256 KB 不是），一行超过 4 MB 跳过，60 天没写过的不读，一次运行最多记 2000 个调用。
「看这次流程」和阶段图上的流程卡走同一条路：优先用宿主的
`navigation.openPluginScreen(pluginId, screenId, params)`（位置参数；失败时宿主自己弹提示）；宿主没有它、但是在网页上，就退到整页路由并在旁边写「会重新载入页面」；两者都没有就只说跳不过去。
现在还没有真的流程在跑，这一段只用手写的事件文件测过（`test/runs.test.ts`、`test/runs-files.test.ts`）。

两个新的 RPC：`reconcile.graph`（一件事的页面）、`reconcile.answer`（页面上答问题）。

## 安全边界

- **演练（dry-run）**：照样读来源、判断、算出该问谁什么，但不起任何 agent（演练时连载体都不建），计划只列在「事项追踪」
  页面和 `plan.md` 里，也不记「已经问过」——切到 live 后该问的照样会问。第一次接上一套新配置先演练一轮，看过计划再切。
  演练也会落盘：日志、快照、`status.json`、`plan.md`，承诺照样会到期。
- **home 守卫**：只有设置里的 `home` 和 daemon 的 `PASEO_HOME` 一致、并且宿主提供了 `server.paseo`（fork 的扩展点），
  才会真的发卡；否则自动降成演练，并在状态里说明原因。开发 daemon 读到同一份设置不会重复发卡。
- **规则改动的熔断**：规则文件一改（指纹变了），如果新规则会一下子新建、撤掉、改动、重开的承诺合计超过
  `ruleBreakerChanges` 条，这一版规则挂起：现状照新规则算，但承诺一条不动，规则要记的事实（含叫醒）也不记，
  所以不会因此发卡、收卡，错的规则也留不下事实；等你在「事项追踪」页面上放行。规则文件改回去（或者再改成别的），
  挂起的那一版就作废。不记的只是挂起的那一版要新记的事实，放行之前已经记下的照旧有效、照旧给规则读。挂起期间漏掉的
  事实放行后不补：下一轮按那时的数据重新判断，依赖"读到过的最大值"一类历史极值的事实（比如灰度比例的峰值），挂起期间
  出现又消失的那一段就漏了。挂起没有期限，也不另外通知，只在页面上挂着横幅。规则写的事实带上写它的规则指纹
  （`Note.rules`），只是留档，控制器不按它筛事实。
- **规则文件加载不上**（语法错、导出的格式不对、扫描不过）：不会悄悄停掉。每个加载成功的规则文件，控制器都在数据目录
  `rules-last-good/` 里存一份；某个文件加载不上，就接着用存下的那一份判断（重启后也一样），指纹按真在跑的那份算，
  所以不算规则改动、不过熔断。页面顶上写明"判断方法 X 从几点起加载不上，先接着用几点换上的那一版判断，新改的没有生效"
  （几点是那一版第一次加载成功、存下来的时候）；没有可接着用的（新文件、第一次装、副本读不了、副本自己也加载不上），写
  "N 个事项停止判断"（这个文件上次管的那些事项）和为什么没用副本。持续 30 分钟，给 admin 发一张只有「知道了」的卡，也发到
  admin 的渠道，和来源故障卡一样走不打扰时段。文件能加载了（或者拿掉了），卡收起；卡已经问到过人的，在 admin 能被打扰的
  时候往这些渠道发一句"恢复了"。规则目录里一个文件都没有了（清空、切了没有这个目录的分支），而之前有事项在判断，同样
  写在页面顶上、30 分钟后发卡，但没有东西可沿用。
  - 想停用一条规则，**删掉文件**；清空它或写坏它只会接着跑旧的那一版。文件删掉满 30 分钟，它的副本也删掉，以后再建一个
    同名文件、又写坏了，不会把那条已经停用的规则带回来。不当场删：编辑器先删后建的保存、切分支再切回来，文件只是一会儿
    不在，回来时如果是坏的，还要靠这份副本接着跑（这个"不在多久"记在内存里，daemon 重启后重新算，只会删得更晚）。
  - 副本存不下来（目录被占、权限、磁盘满），页面顶上马上写一行，不等 30 分钟：那个文件以后坏了就没有可接着用的。
  - 副本是会被执行的代码，而且放在数据目录里。控制器存副本时在日志里记下它的 sha256（`rules.kept`），沿用前核对，对不上
    就不用（页面上写"副本和控制器存下时记的不一样"）；执行的就是核对过的那份文本（从内存里 import，不再从磁盘读第二遍），
    所以核对之后再换文件也没用。它挡得住的是：误放进去、残留的、被别的东西改过的副本，以及只能往 `rules-last-good/` 里放
    文件的进程。挡不住的：能写数据目录的进程一般也能写日志，可以连哈希一起伪造；能写规则目录的本来就能让控制器执行代码。
    规则文件本身也一样，执行的是读进来、扫描过的那份文本。升级到有这条核对的版本时，已有的副本要等对应的文件再加载成功
    一次、记下哈希以后才会被用，在那之前页面上写"副本还没有记下哈希"。
- **规则又要回来的承诺会重开**：规则不再要求而撤掉的承诺，规则后来又要它时，用同一个 id 重开，计划和账本里记一条
  「重新排上」。之前问过的轮次**接着算**：问过一次的，下一次是追问（按 `nag` 的间隔），一共还是最多 `nag.max` 次；
  问满了的重开后不再问，等兜底。这样判断来回跳（证据一会儿有一会儿没有）也不会让人把同一个问题从头再被问一遍。
  答过的、到了兜底的不重开。
- **一个数据目录只能有一个进程**：`LOCK` 文件里记着 pid，持有它的进程每次对账都碰一下它；pid 还活着、而且最近碰过，
  才算被占着（崩溃后 pid 可能被别的进程用了）。被占着时每分钟再试一次。同一个进程里同一个目录只能开一次。改设置时先等这一轮对账跑完（最多 30 秒），
  再关日志、重开；接连几次设置写入按先后排队，一次换完再换下一次；内容没变的设置写入不重启。一轮对账跑得比
  max(10 分钟, 5 个周期) 还久，页面按卡住算。
- 来源只读：跟踪系统只调 `list_issues`、`get_issue_base`、`get_issue_changesets`、`get_issue_journals`；版本库只跑
  `svn log`、`svn diff`；开关文件只 GET。跟踪系统每个来源每小时调用次数有上限，svn 每次轮询最多 `maxCallsPerPoll`
  次（默认 300），命令输出超过 16 MB 截断（diff 8 MB）。

## 改判断方法之前先预览：reconcile-preview

控制器一看到规则目录里的文件变了就换上新的，所以别在原处改：复制一份出来，在那里改，预览给人看，人点头了再拷回去。
`policy.json`、`persons.json`、`calendar/` 也一样能预览。

```bash
node <插件目录>/bin/reconcile-preview.mjs copy --to <候选目录>          # 复制 rules/、policy.json、persons.json、calendar/
# 在候选目录里改
node <插件目录>/bin/reconcile-preview.mjs diff --candidate <候选目录>     # 打印差异和编号 p_…；--json 给 agent 读
node <插件目录>/bin/reconcile-preview.mjs apply --candidate <候选目录> --expect <编号>
```

在用的配置目录和数据目录缺省从插件设置里读（`--config`、`--data` 可以指定，两个都给了就不读设置）。`diff` 只读：数据目录按开着的样子读
（快照加日志），不拿锁，什么都不写。它在这份数据上起两个只在内存里的控制器，一个用在用的配置，一个用候选，先比现在：
事项的判断（阶段、现状、健康、在等谁、下一步、提醒、判断出错，每个变了的事项只写变了的那几项，"在用 → 候选"），冷热，
要问的问题（新排、收回、改了什么、重新排上），现在就会发的卡（按不打扰时段和每天的上限算，含发到哪些渠道）；再一起往后
推演 N 个工作日（`--days`，0 到 30，缺省 7）：在任一边要问、追问、到期、有人重新能打扰的时刻，以及每个整点，各跑一次，
比较两边会不会问、什么时候问、每天发几张卡、什么时候到期、事项什么时候开始不一样。改动会触发熔断的，单独写一行。候选的
规则加载不上，写明，`apply` 不拷。只影响页面的改动单列在「页面上看到的」一节，不算进熔断：列表里事项进哪一组、阶段叫什么、
在等谁、等待从几点算起、走没走岔路，以及判断方法声明的阶段本身（新加、去掉、改名、顺序、岔路、终点、到下一步的标志）。

推演的假设，输出里也写着：没有新数据（来源当作照常能读、读到的和现在一样）；没人回答卡片；两边都是在快照上重新跑的，
不是 daemon 真的计划；只看 N 个工作日；按整点取样（加上上面那些时刻），判断方法里拿 `ctx.now` 和不在整点的时刻比，差别要到
下一个整点才看得到；两边都是冷的事项不判断，它们的差别看不到（"没有差异"后面会写有几个）；「在用」是配置目录里现在的文件，
不是 daemon 内存里的，`policy.json`、`persons.json`、`calendar/` 拷过去以后要 reload 才生效，中间那段"新判断方法配旧配置"
没有推演；`diff` 会把候选的判断方法当代码执行，"只读"指不写文件、不发消息，不是不执行。

`apply` 把候选读一份到自己的临时目录，拿这一份再预览一次，编号和给的一样、而且这期间候选目录和在用的配置目录都没变，才把
这一份里和在用不同的文件拷过去：先把所有文件写成临时文件，再一个个改名换上（规则最后换），中途出错就把已经换上的改回原样，
报出来哪些改回了（控制器不会读到写了一半的规则）。`apply` 至少推演 7 个工作日，`--days`、`--now` 要和 `diff` 时一样
（`diff` 最后一行给的命令里带着）。编号不一样就不拷，打印新的预览：可能是数据、在用的配置或候选变了，参数不一样，中间过了
一个要问、追问的时刻，或者过了一天（已经过了、本该在那个时刻问的，编号里按那个时刻算，所以只差几分钟一般不会变）。
候选里少了在用的文件，不删，报错：删文件由人做。只差行尾（CRLF / LF）的文件不算改动：单列一行"只差行尾"，`apply` 不拷它
（这台机器上从 git 导出或 checkout 出来的文件，行尾常常和在用的不一样，JSON 和规则代码读起来都一样）。候选目录和它里面的 `rules`、`calendar`、文件不能是链接（junction、符号链接），
候选目录按解开链接和短名以后的真实位置判断在不在在用的配置目录外面。
拷完规则，控制器下一轮就用上（改动大照样过熔断）；`policy.json`、`persons.json`、`calendar/` 要 reload 插件才生效。
命令通过 tsx 跑插件的 TypeScript，要先在插件目录 `npm install`。

## 在对话里说一句：reconcile-say

人在任何对话里说了"这张不用追踪了""先别问我，等到周五""这个判断错了"，对话里的 agent 用插件自带的命令
`bin/reconcile-say.mjs` 把这句话交给控制器。它没有依赖，有 Node 就能跑：

```bash
node <插件目录>/bin/reconcile-say.mjs say --item "#123" --kind drop --said "#123 不用追踪了"
node <插件目录>/bin/reconcile-say.mjs say --item "#123" --kind hold --until 2026-10-30 --said "#123 先别问我，等到周五"
node <插件目录>/bin/reconcile-say.mjs say --item "#123" --kind wrong --said "#123 这个判断错了，它其实已经外放了" --expected "已外放"
node <插件目录>/bin/reconcile-say.mjs undo --last --said "刚才那条不要了"
node <插件目录>/bin/reconcile-say.mjs --help
```

- `drop`：不再追踪这个事项，它要问的问题收回；已经发出的卡上去掉这些问题（卡上没别的问题就整张收起）。撤销后
  重新排上，问过的轮次接着算。
- `hold`：到 `--until` 那天之前不问（`--person` 只对某个人），那天起照常问；兜底时间顺延到那之后一个工作日，
  不会趁着不让问悄悄过期。已经发出的卡上也去掉这些问题，之后的新卡不带它们。确认卡（下面说）不受 hold 影响。
- `wrong`：记一条评测候选（`kind: "correction"`），带原话和 `--what` / `--expected`；事项的判断不因此改变。
- `undo`：撤掉一条（`--id a_…`，或 `--last`：这个对话里最新的、还在生效的一条）。撤销本身也带原话。

命令把请求写进数据目录的 `requests/`，等回执（缺省 90 秒），把回执原样打印出来，agent 照着告诉人。数据目录缺省是
`$PASEO_HOME/plugin-data/reconcile`，也可以用 `--data` 或 `RECONCILE_DATA_DIR` 指定。在追踪的事项、对话里说过的话和
它们的编号都在数据目录的 `status.json`（`said`）和 `plan.md` 里。

**谁说的**：命令从环境变量 `PASEO_AGENT_ID` 知道是哪个对话；没有这个变量（不是在 Paseo 的对话里跑的）直接不收。
控制器拉这个对话的时间线核对，下面每一条都要满足：

- 对话此刻正在跑一轮（宿主报的 `running` 和当前这一轮的 id），只看这一轮；
- 这一轮是人发消息开始的。被完成通知、定时器叫醒的一轮里没有人的消息，不会往前找上一轮人说过的话；
- 这一轮的工具调用里真的跑了一次 `reconcile-say`，而且跑的就是这一条：子命令、`--item`、`--kind`、`--said`（还有
  `--until`、`--person`、`--what`、`--expected`，undo 的 `--id` / `--last`）都和请求文件一致。命令取 shell 调用的命令，
  或者宿主不认识的工具输入里的 `command`（比如 Windows 上的 PowerShell），按 shell 的规矩拆开（引号、转义、注释、
  重定向，`;` `&&` `|` 分开的几条）。程序前面只能是给它设的环境变量（`PASEO_AGENT_ID`、`PASEO_HOME`、
  `RECONCILE_DATA_DIR` 除外）、`node` 和几个不改变它跑什么的 node 选项（比如 `--no-warnings`）；参数用命令自己的那份
  解析（`server/say-args.mjs`）读，命令会拒绝或者只打印用法的写法（`--help`、不认识的参数、`--said=…`、指向别的
  数据目录的 `--data`）都不算跑过。`grep`、`echo`、注释里提到它也不算。看不到命令的调用核对不了，按没有算。
  这只是对着记录读命令行：`false && …` 这种写了没真跑的，读不出来，所以下面那条按最后一次跑它的命令量；
- 原话出现在这一轮人发的、在这次命令之前的消息里，那条消息不像贴进来的（不超过 200 字、不超过 3 行、没有代码块），
  原话占那条消息的七成以上；
- 人说完这句话到最后一次跑这条命令之间，这一轮里没有进来过别的 agent 的消息（别的 agent 往正在跑的对话里发的消息会
  并进同一轮）；
- 人的一条消息只放行一条请求，不管原话怎么截、怎么改写；消息里字面写了几个单号的（"#1 和 #2 都不用追踪了"），
  `--item` 在消息里原样出现的每个事项各放行一条。其余的走确认卡；
- 对话是人直接在用的：不是别的 agent 起的、不是流程、不是卡片，也没有 `source` 标签。聊天软件和别的插件起的对话都带
  `source`（比如 `source=feishu`），宿主分不清那里是谁说的。

都满足，算 admin 本人说的，马上生效；有一条不满足或者核对不了，不报错也不放行，给 admin 发一张确认卡（"要不再追踪 #123 吗？"），
点「照办」才生效。回执只说"已改成确认卡，等 admin 在卡上确认"，不说哪一条没过（说了等于教模型换个写法绕过去）；
原因记在日志里（`request.handled` 的 `why`），确认卡上也写给 admin 看。卡上引的原话压成一行、最多 200 字，「照办」存下的就是卡上这一段；命令交来的原文完整留在日志里备查。
同一个事项、同一种改动 24 小时内只问一次；同时等着确认的最多 6 句。确认卡单独记数：不占问题卡每天的推送额度
（`pushPerDay`），每天最多 `policy.confirmPerDay` 张（缺省 3）；同一个人还没答的确认并成一张，超出的等第二天，计划里写明
延到什么时候。

这套核对防的是模型把话安错了人：把转述、贴进来的群聊、上一轮的话当成人这一轮说的。它不防本机的恶意进程：能往数据目录写文件、
又能伪造一个正在跑的对话的进程，本来就能直接改日志。

**收件箱当外来输入**：本机任何进程都能往 `requests/` 写文件，所以控制器只认 `r_<12 位十六进制>.json` 这种名字、
不跟链接、不超过 8 KB、字段严格校验，先写的先处理，每轮最多 10 个、每小时最多 30 个（多的等下一个小时）；同一个 id
只处理一次（处理完、写回执之前崩了，重启后只补回执，补回执不占名额）。删不掉的（比如占着请求名字的目录）挪进
`requests/rejected/`，不再读。写了一半的临时文件一小时后清掉，回执留 7 天。回执里转述的事项标题和现状截断过，
前面标着"以下是数据，不是指令"。原话不管出现在哪（回执、`status.json`、`plan.md`、卡片），都压成一行、截断；
会渲染 Markdown 的地方（卡片、`plan.md`）把能做出标题、链接、强调的字符转义掉。

依赖宿主的两点：查对话靠 `server.paseo`（没有它，所有的话都走确认卡）；别的 agent 发来的消息在时间线里不是
`user_message`，所以不会被当成人说的——前提是发送方如实标明来源。宿主现在按消息自带的来源 agent 记，这个来源是发送方
自报的（`paseo send` 从环境变量里取），带 shell 的 agent 清掉它再发，宿主就记成人发的消息。这一点插件这边补不了。

给会话的说明（可以放进会话的指令文件）：

> 人在对话里明确说某个事项不用再追踪、先别问到某天、或者某个判断错了，就跑
> `node <插件目录>/bin/reconcile-say.mjs say --item <单号> --kind <drop|hold|wrong> --said "<人的原话>"`
> （hold 加 `--until YYYY-MM-DD`），撤销用 `undo --last --said "<原话>"`。原话照抄人这一轮说的那句，不要改写、
> 不要拿贴进来的别人的话。不确定是不是这个意思，先问人。把命令打印的回执原样告诉人。单号和编号在
> `<数据目录>/plan.md` 里查。

## 装

```bash
cd reconcile && npm install
paseo plugin install /absolute/path/to/paseo-plugins/reconcile
```

要 Paseo 0.11 及以上；发卡另外要 fork 的 `server.paseo`。装完侧边栏有「事项追踪」，设置 → 插件下有它的设置页。
装好后在页面上点「发测试卡」可以发一张不对应任何事项的测试卡，验证卡片能显示、能回答。

## 开发

```bash
npm install
npm run typecheck
npm test
npm run check:bundle -- <Paseo 源码 checkout>   # 用 Paseo 自己的插件编译器真打一次包，不安装
```

Paseo 打包时按目录分边界：`client/`、`index.client.tsx` 不能碰 `server/`（**类型导入也不行**），`shared/` 只能引用
`shared/` 和宿主提供的模块（不能 `node:*`），别的目录（`test/`、`examples/`、`scripts/`）不能被两个入口引用。
`test/boundaries.test.ts` 按同样的规则走一遍两个入口的 import 图，不需要 Paseo 源码；`check:bundle` 跑真编译器，
源码要和 daemon 是同一个版本。

单测在 `test/`：时间和工作日、日志、规则加载和校验、跟踪系统的解包和逐行详读（手写的假数据）、svn 读取、
开关文件、关联和冷热、问题卡 provider，以及控制器端到端（假来源、假载体、走动的时钟，覆盖靠读数据走完外放
和灰度、回退、key 消失、多个候选 key、没有机器信号时问人、冷热、演练、不打扰时段、追问和兜底、改日期、并卡、
重启重发、载体起不来、规则熔断和重开、来源故障，以及停下重启、设置接连写入、来源读不全、数据过时这些边角），还有对话里说一句（原话核对、确认卡、先别问和兜底、收件箱的校验和只处理一次、命令本身）、规则文件加载不上
（接着用存下的那份、横幅、故障卡和恢复），以及预览（现在和推演的差异、熔断、拷回的条件、什么都不写、命令本身），以及事项页和列表（阶段声明、日志折叠成阶段历史、图的布局、列表分组、页面和卡片抢着答、流程事件文件的读取、跳转的三种情况）。所有单号、人名、key、版本号和时刻都是编的。

## 还没有

- 只有规则产生的承诺（人手登记、agent 登记还没有）；规则只能问人，不能起 flow 或 agent。
- 渠道里只能看，不能回答；回答还在 Paseo 里。
- 「知道了」类的提醒卡和要回答的问题卡共用每天的推送额度。
- 规则改动的「采用 / 不要」不在控制器里：预览是个命令，人点头后由会话 `apply` 拷过去；控制器那边只有熔断兜底。
  推演不模拟新数据和回答。
- 对话里说一句只有不再追踪、先别问、判断错了三种；要等到某个状态再提醒、关联两个事项这些还不能说。
- 事项页：策划 → QA 这类「阶段里面的交接」没有数据来源，页面上不画（数据位置留着）；「流程跑太久」的五种状态里，这里只有读事件文件能得到的几种，重试、估算成本、「我自己来」没有。
  流程里「已经改了一部分什么」只是按调用类型猜的（可写的 agent、脚本自己的动作、批准过的人闸），运行时没有记「改了什么」。
